# 第一章 项目定位

## 1.1 产品定位

《汉语起步》面向来中国学习、生活的国际学生，围绕汉语学习中的**听、说、读、写、用**五个方面，提供结构化课程、互动学习、教师教学支持及真实情境交际活动。

平台长期不仅服务学生学习，还应支持教学实践、学习过程分析和教育技术研究。

## 1.2 长期发展方向

平台将逐渐具备以下能力：

| 能力 | 主要内容 | 实施定位 |
|---|---|—|
| 汉语教学 | 课程、发音、阅读、书写、练习 | 核心 |
| 教师支持 | 班级、任务、学习监测、反馈 | 核心 |
| 情境交际 | 生活场景、角色扮演、交际任务 | 逐步扩展 |
| 真人协作 | 双人组队、小组学习、在线对话 | 后续 |
| AI 学习伙伴 | AI 同伴、情境角色、可教智能体 | 后续 |
| 学习研究 | 行为事件、学习分析、研究数据 | 底层预留，逐步增强 |
| 多模态研究 | 眼动、面捕、EEG 等 | 成熟阶段 |

长期需求不自动进入首发范围。

## 1.3 项目建设原则

1. 教学设计先于具体功能实现。
2. 保留已有网站原型和有效的教学交互。
3. 课程、学习事件、评价规则分别管理。
4. 学生个人数据和正式研究数据分开治理。
5. 当前按一人开发进行工程规划。
6. 不提前开发尚未需要的复杂系统。
7. 数据必须能够备份、恢复与跨云迁移。
8. 正式上线需要独立的验收和批准。

- 邀请学生。

- 查看授权学生的实时学习状态。

## 3.3 管理员 Administrator

- 管理学生与教师账号。
- 管理角色。
- 管理班级。
- 管理课程发布状态。
- 维护必要的系统配置。
- 记录重要管理操作。

- 研究项目管理。

- 事件与实验版本查询。

- 班级可以有多个授权教师。
- 教师只访问其授权范围内的数据。
- 不因为学生加入多个班级而自动共享全部学习记录。

首版不建设多机构、多租户 SaaS。

# 第四章 教学体系：听、说、读、写、用

## 4.1 听

教学内容：

- 拼音语音辨别。
- 声调听辨。
- 词句听力。
- 情境对话理解。
- 听后作答。

互动：

- 音频播放。
- 重复听音。
- 选择与匹配。
- 听力理解题。

学习数据：

- 播放开始。
- 播放进展。
- 有效播放覆盖。
- 作答及提示。
- 活动完成状态。

## 4.2 说

教学内容：

- 发音模仿。
- 声调练习。
- 词句朗读。
- 简单口语问答。
- 情境交际。

互动：

- 示范音频。
- 麦克风录音。
- 自我回放。
- 重新录制。
- 教师反馈。
- 后期真人或 AI 对话。

发音表现与录音技术成功必须分别判定。

## 4.3 读

教学内容：

- 拼音认读。
- 汉字识别。
- 词语理解。
- 句子阅读。
- 生活场景文本理解。

互动：

- 词语匹配。
- 句子阅读。
- 阅读后作答。
- 情境标识识读。

不能把页面停留时间直接等同于理解程度。

## 4.4 写

分为两个方向。

### 拼音书写

- 四线三格展示。
- 字母书写示范。
- 字母位置与形态。
- 声调符号。
- 拼音输入。
- 描写与独立书写。

### 汉字书写

- 汉字字形。
- 笔画。
- 笔顺动画。
- 田字格。
- 描红。
- 独立书写。
- 笔顺和字形反馈。

优先采用 SVG、Canvas 等实现动态书写。GIF 可以作为教学资源，但不应成为唯一方案。

可评估 Hanzi Writer 等工具，正式集成前核查适用的代码和数据许可。

书写数据不默认采集全部原始笔迹；高频轨迹采集需根据教学或研究目的单独确定。

## 4.5 用

**“用”是把所学汉语运用到真实或模拟情境中的综合能力。**

主要场景：

- 食堂点餐。
- 图书馆问询。
- 宿舍交流。
- 校园问路。
- 购物。
- 交通。
- 向教师提问。
- 与同学共同完成生活任务。

活动形式逐步发展为：

个人情境练习 → 真人角色扮演 → AI 角色对话 → 小组协作。

评价重点包括：

- 交际目标是否达成。
- 回应是否相关。
- 表达是否准确、适切。
- 是否能完成场景任务。

不要求学生机械复述唯一标准句子。

# 第六章 学习事件与教学评价

## 6.1 事件系统目的

实现：

- 学习行为可靠记录。
- 学习进度计算。
- 教师实时学情。
- 学习历史重建。
- 教师反馈关联。
- 后期经授权的科研分析。

## 6.2 标准事件结构

至少包含：

- `event_id`
- `event_type`
- `schema_version`
- `session_id`
- `lesson_id`
- `lesson_version`
- `activity_id`
- `occurred_at`
- `received_at`
- `payload`

身份由服务端可信上下文确定。

## 6.3 基础事件

| 事件 | 含义 |
|---|—|
| `session_started` | 会话开始 |
| `lesson_entered` | 进入课程 |
| `activity_entered` | 进入活动 |
| `audio_started` | 音频开始播放 |
| `audio_progress` | 真实播放进展 |
| `audio_seeked` | 音频跳播 |
| `audio_completed` | 自然播放结束 |
| `audio_validated` | 服务端确认播放规则 |
| `answer_submitted` | 提交答案 |
| `hint_requested` | 请求提示 |
| `feedback_viewed` | 查看反馈 |
| `activity_completed` | 活动满足完成条件 |
| `lesson_completed` | 课程满足完成条件 |
| `session_ended` | 会话结束 |

后续增加教师反馈、任务、书写和协作事件。

## 6.4 事件可靠性

必须支持：

- 唯一事件 ID。
- 重复上传幂等。
- 相同 ID、不同内容冲突检测。
- 服务端数据校验。
- 网络失败补传。
- 事件持久化。
- 历史查询。
- 服务重启后恢复。
- SSE 断线后的查询补偿。
- 事件字典版本化。

**原始事件记录行为，学习状态由规则计算。**

## 6.5 有效听音

暂定默认技术标准：

**播放覆盖率 ≥90%。**

覆盖率按真正播放的媒体时间区间并集计算。

- 跳播区间不算覆盖。
- 重复片段不重复计入。
- 可以通过补听达到要求。
- 单次明显跳播可记录但不永久判失败。
- 关键片段可要求完整覆盖。
- 音频自然播放结束不等于达到覆盖要求。
- 有效播放不意味着真实理解。

规则版本：`audio_coverage_v1`。

## 6.6 学习会话

默认：

**连续 30 分钟没有有效学习活动，判定会话超时。**

有效活动包括：

- 主动进入活动。
- 提交作答。
- 请求提示。
- 有效音频进展。
- 录音操作。
- 书写提交。
- 真实教学互动。

不包括：

- 页面静置。
- 无意义鼠标移动。
- 自动心跳。
- 后台同步。
- 补传历史事件。

规则版本：`session_activity_v1`。

上述完整会话判定在实际课程开发阶段实现，不强制在 V0.0 完成所有细节。

# 第八章 录音与媒体存储

## 8.1 已确定方案

**腾讯云 COS 为主媒体对象存储。**

但现在课程设计尚未完成，不立即开通和接入。

V0.2 实现正式录音持久化时再接入 COS。

## 8.2 录音流程

学生录音 → 本地回放 → 请求上传授权 → 私有 COS 上传 → 服务端验证 → PostgreSQL 保存媒体元数据 → 教师授权回听。

## 8.3 录音有效性

分为：

1. 技术有效：文件存在、可解码、时长符合要求。
2. 声音可用：无明显全静音或严重异常。
3. 发音表现：是否符合教学目标。

初期技术有效时长下限暂定为 1 秒；具体规则须在 V0.2 录音实现前完成设备测试并冻结。

## 8.4 录音保存

普通发音练习录音默认保存 7 天。

需实现：

- 私有存储。
- 到期删除。
- 删除失败检查。
- 教师访问授权。
- 备份副本的期限管理。
- 旧备份恢复后的过期清理。

正式研究录音单独制定政策。

## 8.5 可迁移存储

提供统一 StorageService。

开发环境可以使用本地文件系统。

正式环境使用腾讯 COS。

业务代码不能依赖固定的本地路径或永久 COS URL。

无需现在实现阿里云 OSS 等所有适配器。

# 第九章 情境交际、协作与 AI

## 9.2 真人协作

后期支持：

- 学生 A 与学生 B 组队。
- 角色分配。
- 轮流用中文交流。
- 交换角色。
- 任务完成评价。
- 教师反馈。

后期支持：

- AI 情境角色。
- AI 口语伙伴。
- AI 学习同伴。
- AI 可教智能体。

任务评价重点为交际目标、表达适切性、互动回应和必要的语言表现。

AI 可以辅助评价，但不能在未经验证的情况下直接给出具有正式效力的成绩。

## 9.5 实施边界

这些属于未来教育功能发展方向。

不加入 V0.0 最小系统，也不自动要求首发实现。

逐步支持：

- 研究项目。
- 实验条件。
- 实验分组。
- 干预配置。
- 数据质量检查。
- 去标识化导出。

## 10.3 多模态科研

成熟阶段根据研究问题再考虑：

- 眼动数据。

- EEG。
- 多模态时间同步。

# 第十一章 技术架构

## 11.1 技术方案

| 层次 | 选择 |
|---|—|
| 前端 | React + TypeScript + Vite |
| 后端 | FastAPI |
| 数据库 | PostgreSQL |
| 数据库迁移 | Alembic |
| Web 入口 | Nginx |
| 实时学情 | SSE + HTTP |
| 未来实时文字互动 | WebSocket |
| 未来音视频 | RTC |
| 媒体 | 腾讯 COS |
| 代码管理 | GitHub 私有仓库 |

React 是当前首选，应通过真实课程迁移验证实施效果；不为框架迁移而丢弃现有原型的 UI 和交互。

## 11.2 工程原则

采用模块化单体应用。

长期可以形成：

- Identity。
- Course。
- Learning。
- Event。
- Classroom。
- Assignment。
- Feedback。
- Media。
- Scenario。
- Collaboration。
- AI。
- Research。
- Analytics。
- Backup。

**这不是 V0.0 的建目录清单。**

V0.0 仅建立模拟身份、基础会话、事件写入与教师测试通知所需的结构。

## 11.3 当前服务器

腾讯云 Ubuntu 24.04，已知约：

- 4 核 CPU。
- 3.6 GiB RAM。
- 1.9 GiB Swap。
- 40GB 系统盘。

初期部署 Nginx、FastAPI、PostgreSQL 和前端静态文件。

避免在服务器系统盘长期保存大量录音或录像。

## 11.4 环境分离

- 本地开发：模拟数据。
- 腾讯云私有测试：内部联调。
- 正式生产：通过发布批准后启用。

私有测试服务默认通过本机回环地址和 SSH 隧道访问，不暴露未授权测试 API 或数据库。

# 第十二章 数据库与基础事件设计

## 12.1 V0.0 数据库

只建立：

| 表 | 用途 |
|---|—|
| `test_actors` | 私有测试模拟身份 |
| `learning_sessions` | 学习会话 |
| `learning_events` | 原始学习事件 |

V0.0 不建立完整用户、班级、AI、协作或科研数据库。

## 12.2 V0.0 示例事件

先实现：

- `activity_entered`
- `answer_submitted`
- `hint_requested`

这些用于验证接口、存储、查询和实时通知，不代表已经完成第一课的真实教学规则。

## 12.3 可靠性要求

- 事件 ID 唯一。
- 重复事件不会重复计分。
- 同 ID 不同内容视为冲突。
- 服务端负责可信身份关联。
- 数据持久化成功后确认。
- SSE 不作为唯一历史来源。
- 客户端网络恢复后可以补传未确认事件。
- 历史事件可以查询并恢复。

# 第十三章 备份、恢复与云厂商迁移

## 13.1 基本目标

即使腾讯云服务器和 COS 同时无法使用，项目仍能利用独立备份在其他厂商重建。

## 13.2 备份内容

- 项目代码。
- PostgreSQL。
- 课程内容。
- 教学媒体。
- 仍需保留的录音。
- 部署配置。
- 数据库迁移版本。
- 备份清单。
- 独立保护的恢复凭据。

## 13.3 备份策略

至少建立：

1. 腾讯云运行数据。
2. 本地加密备份。
3. 腾讯云外独立副本。

本地备份支持 Mac 和 Windows。

## 13.4 备份工具

规划：

- `backup`：生成备份。
- `verify`：检查备份。
- `restore`：引导式恢复。

自动备份和恢复能力随版本逐步完善。

## 13.5 备份频率

初期建议：

- 重要代码变更即提交 Git。
- 数据库每日备份。
- 课程媒体重要变更后同步。
- 每月恢复演练。
- 重大更新前执行完整备份。

真实学生数据启用后，重新评估频率和数据保留政策。

## 13.6 恢复目标

暂定：

- RPO：争取不超过 24 小时。
- RTO：争取 4 小时。

上述目标需要经过恢复演练验证。

涉及新厂商备案接入等外部步骤时，公开重新上线时间可能更长。

## 13.7 跨云迁移

必须能够：

- 在新 Ubuntu 服务器部署程序。
- 恢复 PostgreSQL。
- 迁移媒体对象。
- 更换存储适配器。
- 恢复必要配置。
- 验证权限、课程和学习记录。
- 处理域名、证书及适用备案。
- 验收后切换服务。

# 第十四章 安全、隐私与长期维护

## 14.1 系统安全

正式账号阶段必须实现：

- 安全密码哈希。
- 服务端认证。
- 安全 Cookie。
- CSRF 防护。
- 登录限流。
- 服务端权限校验。
- PostgreSQL 公网隔离。
- 私有 COS 访问。
- 密钥分离。
- 必要操作审计。

## 14.2 数据安全

- 测试数据与正式数据隔离。
- 真实学生信息不提交 GitHub。
- 教学数据与科研数据分层管理。
- 备份加密。
- 文件到期删除。
- 恢复后重新执行适用的过期清理规则。

## 14.3 可维护性

- GitHub 私有仓库。
- 规范化目录。
- TypeScript 类型检查。
- API 契约。
- 数据库迁移。
- 自动化测试。
- 依赖管理。
- 部署文档。
- 备份恢复演练。
- 监控与告警。

目前只按一名开发者实际承担工作来规划。

未来团队增加后再逐步启用 PR 审核、分支保护和更完整的 CI。

# 第十九章 最终实施原则

**一、保留长期方向，但不提前开发全部未来功能。**

**二、目前先审查第一课、建立工程、验证最小事件闭环。**

**三、课程完成、学习评价与任务完成必须分开。**

**四、教学行为数据必须可靠、可解释、可追溯。**

**五、教师看到的学习信息应能够支持真实的教学行动。**

**六、普通教学数据与正式研究数据需要分别治理。**

**七、腾讯云服务器和 COS 可以替换，代码、数据库及重要文件应可恢复。**

**八、平台首发完成不等于长期建设结束，后续持续迭代。**

**九、任何新需求先判断所属版本，不因为加入长期蓝图就自动成为当前任务。**

# 结语

《汉语起步 Hanyu Start》的长期目标，是成为一个以高质量汉语教学为基础、以“听、说、读、写、用”为核心、融合教师指导、真人协作、AI 学习伙伴和规范教育研究的可持续平台。

其建设不以一次性完成功能数量为目标，而以**教学质量、学习数据可信度、科研严谨性、系统可靠性和长期可维护性**作为衡量标准。

**当前的实际起点是第一课教学审计和 V0.0 学习事件闭环，不是建设整个长期平台。**
